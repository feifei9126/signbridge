# 第六阶段：小批量补词闭环与发布前验收

## 本轮做什么、不做什么

把前五轮连成可重复的工作流程：**真实字幕 → 缺词频次 → 每批最多 8 个候选 → 制作草稿 → 动作验收 → 人工确认启用 → 重新测覆盖 → 小范围试用**。

本轮不重新调整已确认的模型大小、位置、浮窗控制、骨骼轴或手形参数；不凭空编造词语对应的动作，不用同义词别名凑数，也不自动向 GitHub 发布。当前内置目录仍为 **52 个 SIGNS、172 个查找别名、16 个 CHARS 回退**。它是词典驱动的辅助原型，不是完整的中国手语句法翻译系统。

**没有新的人工作品或核验依据时，不能把“代码运行正常”写成“新增标准手语已通过验收”。** 本轮新增的是补词管理与验证能力，真实新增词条需要按以下流程制作和审核。

## 备份与恢复边界

改动前快照标识：`phase6-20260922-143324`，由维护者保存在仓库外的本地备份目录，不随源码发布。

`project.tar.gz` 已通过 `SHA256.txt` 校验，保存第五轮已验收工作目录，包括尚未提交的修改。排除 `.git`、用户 `exports/`、依赖、旧备份、CodeGraph 和测试临时产物。恢复前先另存当前目录，然后将快照解压到独立目录比对；不要用 `git reset --hard` 丢弃前五轮修改。

快照不含浏览器动作库或 IndexedDB 视觉基准。恢复代码不等于恢复浏览器数据：动作库另行导出动作包；视觉基准下载 PNG 和 JSON；补词清单可下载进度 JSON 留档，但本轮不支持清单 JSON 导入。

## 使用入口

1. 在 `chrome://extensions` 重新加载当前 `signbridge/dist/`，关闭旧控制面板和旧工具页，再打开控制面板 → **词库覆盖分析**。
2. 粘贴实际使用场景的文本，或导入 UTF-8 TXT / SRT / VTT。点“分析当前词库”。
3. 按频次和上下文选词，点击未覆盖词旁的 **加入本批**。最多 8 个，不默认全选、不自动保存全部缺词。
4. 分词不等于手语词义边界。需要完整表达时，使用“手动加入完整词组”，最多 100 字符；例如可保留一个完整词组而不是机械地为拆开的字逐个建动作。
5. 清单中的“姿势编辑器 / 录制工具”仍只预填名称和匹配文字，不把当前姿势当成该词的正确动作。
6. 制作并保存草稿后，点击 **动作验收**；在目录里按名称找到保存的动作，完整回放并检查三视图。此按钮打开目录，不自动选中或批准动作。
7. 核验手形、方向、位置、运动和节奏后，回到原编辑/录制页预览，再明确确认用于翻译。
8. 返回覆盖页查看状态，并用**同一份原始材料重新分析**。最后在真实视频里验证字幕、连续播放和视觉表现。

### 状态含义

| 状态       | 判断依据                                                             | 不代表什么                                               |
| ---------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 待制作     | 运行时不能完全匹配，也没有同匹配文字的已保存候选                     | 不证明该词一定要单独制作，先检查语境                     |
| 已保存候选 | 存在相同匹配文字的记录，但运行时尚未完全匹配                         | 不证明动作已启用或含义正确                               |
| 可完全匹配 | 使用当前运行时匹配器和真实启用记录，所有词被命中，无遗漏、跳过或截断 | 不保证句法、完整意思或手语正确；也可能由多个现有动作组成 |
| 状态未核验 | 模型或存储读取失败                                                   | 不会冒充“缺词”或导出过期的成功结果                       |

清单显示真实动作 ID，保存、启用、停用或修改动作后会自动重算。保存修改会撤销动作原有确认，因此状态也应回到候选。两页并行修改通过同一个写入锁串行处理，避免互相覆盖。锁不可用时停止写入；损坏记录不静默重置，用户明确清空后才重建。

刷新保留清单，**不保留分析原文**。移出词或清空清单不删除动作、启用记录或视觉基准。导出进度会重新核对，不沿用上一次缓存。JSON 包含所选词、实际命中 ID、候选 ID、扩展版本和时间，并明确 `linguisticReview: "not-assessed"`；它不是审核证书。

### 第一批如何选

建议先选一个场景，例如就医、上学或日常交流，只做 5–8 个高频缺口，而不是同时扩展几十个词。可考虑“医院、医生、学校、老师、学习、工作、时间、家人”等**候选方向**；这不是已经统计过的高频榜，也不是本轮新增动作。最终以自己材料的频次、语境和手语使用者反馈为准。

每个候选至少记录：完整含义、适用语境、动作来源及授权、制作者、核验者、动作 ID、核验日期、已知不足。请邀请熟练手语使用者参与，不能只由不懂手语的开发者看“像不像”。

## 实际使用验收表

在同一批材料和同一扩展版本下复测，保留失败项，不用“有动作”替代“表达正确”。

| 项目       | 操作                                            | 通过标准                                                     |
| ---------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 单词含义   | 逐个回放本批动作，并让手语使用者解释            | 含义与匹配文字一致，手形/朝向/位置/运动/节奏正确             |
| 连续动作   | 播放包含多个目标词的真实字幕                    | 顺序合理，无突跳/持续堆积；单句 12 个动作上限有清晰理解      |
| 姿态稳定   | 检查正面和两侧、长时间连续播放                  | 无明显穿模、反向或累计偏移；不能只查目标关键帧               |
| 网站字幕   | 在 B 站及至少一个目标视频网站分别测试           | 可用字幕进入翻译；没有字幕、纯画面烧录字幕时不冒充已识别     |
| 播放操作   | 暂停、继续、拖进度、换视频、关闭后重开          | 不播旧内容，不生成重复浮窗，原鼠标控制仍可用                 |
| 标签页声音 | 由用户主动开启，分别选本地 Whisper / 已配置云端 | 识别的是视频标签页音频；停止后释放采集；失败可见，不伪装成功 |
| 隐私       | 检查导出和反馈文件                              | 无 token、私密字幕或未授权素材；所选词也可能包含隐私         |
| 恢复       | 另存动作包，禁用一个新动作后再测                | 不影响旧动作；坏批次可停用或从已校验备份恢复                 |

浏览器自动化使用本地测试网页、隔离配置和合成测试动作；不会调用用户云端 API、下载 Whisper 大模型、录制真实音频或替用户确认手语。**上述真实站点、音频服务和语言验收仍需人工执行。**

## 一条命令执行发布前自动化

先准备兼容扩展加载的 Chromium 和 Playwright。脚本不会替用户自动安装浏览器或大型依赖。

```bash
cd signbridge
# 若环境能直接 import playwright 且已有兼容 Chromium，可不设置这两项。
# 自定义安装位置时使用自己的绝对路径：
export SIGNBRIDGE_PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs
export SIGNBRIDGE_CHROMIUM_PATH=/absolute/path/to/chromium
npm run verify:release
```

执行顺序：

1. `npm run verify`：构建、ESLint、Node 回归、格式检查；检查源码、lockfile、manifest 与构建版本一致。
2. 依次运行 `tests/browser-phase1.mjs` 至 `tests/browser-phase6.mjs`，包括真实 GLB 的加载、页面交互和截图。
3. 记录源码及构建文件的 SHA-256；验证过程中变化则失败，避免“测试旧数据、发布新文件”。
4. 输出 `test-results/release-acceptance.json` 和各阶段独立证据。任一阶段失败立即停止并返回非零码；每次先写入运行中状态，不拿上次成功报告冒充本次结果。

只有 `automatedStatus: "passed"` 表示本次自动化通过。报告中的 `publishReady` 始终为 `false`，人工验收项保持 `pending`：脚本不替人作语言、授权、真实站点或 ASR 决策。运行中被中断的报告也不能当作通过。生成文件在忽略的 `test-results/`，不包含用户浏览器存储。

### 发布与反馈

第六轮开发与验收本身不改版本号、不自动提交、不打 tag、不推送 GitHub。后续维护者可单独批准源码同步；源码同步不等于已完成手语语义验收或发布正式发行包。正式发布前应：

- 完成实际使用验收表，并记录具体环境、成功与失败项。
- 在独立发布说明里写明新增能力和限制，不宣传“准确翻译全部视频”。
- 若批准发布，同步更新 `package.json`、`package-lock.json` 和 `manifest.json` 版本，再重新执行发布验收。
- 只分发通过验收的 `dist/` 构建；记录构建 SHA-256。不能把 `test-results/`、`node_modules/`、`exports/` 或密钥一起打包。
- 先小范围试用，再根据反馈扩展下一批动作。反馈至少含版本、网站/输入来源、复现文字（脱敏）、实际动作 ID、期望含义与三视图证据。

## 本轮自动化覆盖

- 纯逻辑：输入限制、归一化去重、并发追加、上限、损坏数据保护、显式清空、失效确认、跳过词/部分匹配不能算完成、存储订阅清理、三语文案。
- 真实浏览器：加入、刷新、跨页同步、工具预填、草稿→启用→再保存、报告导出、验收入口、删除/取消、坏记录恢复、模型失败重试、完整词组与批次上限。
- 前五轮浏览器检查继续作为回归门槛。
- 受保护文件与本轮修改前快照逐字节比较，避免无意修改已确认动作和浮窗。

以上验证是对指定场景的证据，不是“整个项目从此没有任何错误”的保证。
